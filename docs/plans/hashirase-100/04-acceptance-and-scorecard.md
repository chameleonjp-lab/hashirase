# 04 合格条件・受入検査・採点

## 1. 100点の定義

従来の85/70/65/35/30/35点は、試作への暫定評価です。この計画では、仕様と証拠を結び付けるため採点方法を新しく定義します。以前の数字と連続した精密測定値として扱いません。

各評価軸を5要求に分け、各要求は20点です。対応する2件の検査および数値条件が全て合格し、証拠があれば20点、未達・未検証なら0点とします。途中の達成率は別欄に書けますが、満点へ丸めません。

| 評価軸 | 100点の構成 |
|---|---|
| 企画・機能の豊富さ | R01〜R05：2モード、選択読込、案内、繰返し遊び、車両試験 |
| ゲームシステム | R06〜R10：独立性、状態遷移、交通、5台追跡、公平な得点 |
| 車両・物理表現 | R11〜R15：ゲーム走行、現実寄りモデル、衝突、損傷、根拠と再現性 |
| スマートフォン操作性 | R16〜R20：縦横の動的起点スワイプ、PC/混在入力、キャンセル、端末別感度・代替操作 |
| 描画性能への配慮 | R21〜R25：周辺生成、まとめ描画、持続性能、資源管理、起動 |
| 安定性・保守性 | R26〜R30：復旧、保存、検査、安全性、証拠と公開 |

**6軸それぞれ100点、重大問題0件が完成条件です。平均100点や総合点で代替しません。**
起動不能、操作不能、未選択モードの先読み、追跡6台以上、状態漏洩、重大な情報漏洩、保存全消失が1件でも残れば公開完了判定を止めます。

## 2. 試験の共通条件

自動検査は同じseed・設定・入力列で再現できるものにします。測定にはcommit SHA、build識別値、端末・OS・ブラウザ、viewportとpixel ratio、画質、交通量、天候、補助、試験開始終了時刻を必ず付けます。

一次基準はiPhone 17 ProのSafariと、型番・CPU/GPU・OSを記録した1台のPCです。iPhoneの正確な画面サイズは実機で読んで保存し、既存スクリーンショットの393×852を機種固有寸法と断定しません。PCの型番はT01時に利用可能な環境を登録し、性能を測れない場合は未検証とします。

自動ブラウザはChromium/Firefox/WebKit。画面サイズ・タッチの模擬検査と、iPhone本体での試験を区別します。PC実機がない場合に、CIの描画速度を実PC性能として代用しません。追加の有料クラウド契約やPC購入はこの計画の前提ではありません。

## 3. 数値の合格基準（提案値）

これらは実測結果ではありません。T01で測定環境を固定し、T02以降は黙って閾値を下げません。変更する場合は、理由・端末・品質への影響を別の仕様変更としてレビューします。

### 物理計算

| 検査 | 初期条件・合格値 |
|---|---|
| 一定力 | 抵抗なし、1000kg、1000N、初速0、10秒。速度10m/s±0.01、位置50m±0.10 |
| 自由落下 | 接地なし、重力9.80665、2秒。落下速度19.6133m/s±0.03、距離19.6133m±0.10 |
| 静的荷重 | 平地・静止。四輪の法線力合計とmgとの差≤1%。負の接地力なし |
| 摩擦 | 全接地輪で合成タイヤ力≤mu×法線力＋1%の数値許容。非接地輪の路面力0 |
| 制動 | 理想化した一定摩擦fixtureでv²/(2mu g)と停止距離の差≤5%。四輪の総合モデルは同条件反復差≤1% |
| 孤立衝突 | 無外力の2物体で運動量差≤1%。反発係数≤1の試験で運動エネルギーが1%超増えない |
| 描画非依存 | 同じfixed tick入力で30/60/120fps相当を比較。純粋モデルの状態最大差≤1e-6。実ブラウザ間は位置差≤0.05m、速度差≤0.05m/s、姿勢差≤0.5度（10秒fixture） |
| 反復 | 同seed/同入力/同条件を5回。値が許容差を越えたら乱数・時間依存を調べる |

これらは解析解との整合性を調べる試験です。実車のTeslaと数値が一致することを証明しません。未確認パラメータを正しそうな実測値として埋めません。

### 性能と資源

| 項目 | 提案する合格値 |
|---|---|
| ホーム | gzip相当150KiB以下。10Mbps/RTT100ms/cold cacheで5回、操作可能までp95≤2秒 |
| 初期モード | 走行可能になるまで追加取得4MiB以下。同条件5回、p95≤8秒。遅い素材は必要時取得 |
| 60fps設定 | 試験場で中央値≥58fps、描画間隔p95≤25ms、p99≤50ms |
| 30fps設定 | 市街地/四輪試験で中央値≥29fps、描画間隔p95≤40ms、p99≤67ms |
| 入力応答 | 入力イベント受付→画面反映p95≤100ms（30fps）、≤66ms（60fps）。デバイス全遅延ではなくアプリ測定と明記 |
| 走行中の停止 | ロード画面を除き1秒以上の固まり0回。200ms超の処理があれば原因と改善を記録 |
| モバイル描画 | 標準画質でdraw calls≤350、triangles≤500,000を初期予算。影等を含む数え方を固定 |
| 再利用プール | 煙・破片・雨・跡に上限あり。30分後も上限を越えない |
| モード終了 | activeSession/RAF/所有する音源/未解放モードGPU資源は0。共有UIの固定イベントは除外し数を記録 |
| キャッシュ | 共有画像等の推定容量96MiB以下を初期予算。実GPU/JSメモリの完全測定と混同しない |

場面は、試験場通常走行、都市交通85台、追跡5台＋検問＋ヘリ、雨＋衝突演出、シミュレーター四輪試験、20回のモード切替です。各短期計測は30秒warmup後180秒を3回。最も重い条件で30分の持続試験を行い、最初と最後の性能を両方残します。

画質を落としても信号・交通・当たり判定・得点・物理の更新数をこっそり削りません。60fps未達なら30fpsへ選べる案内は可能ですが、60fps項目を合格にしません。ユーザーが選べる高画質も未検査のまま「快適」と表示しません。

## 5. 証拠と完了判定

各検査は `testId/status/commit/build/environment/seed/settings/command/observed/expected/evidence/reviewer` を保存します。失敗時は再現操作と不具合IDを付けます。現在の計画にあるコマンドはまだ実行したものではありません。

短い要約は連絡に使えますが、正式ログ、監査内容、通信一覧、GitHub Actionsの実行記録を省略して保存しません。秘密情報はそもそもログに含めない設計にします。必要な画像は担当者が実見し、確認した画像と条件を記録します。

通常PRは変更に関係する短い試験と構文・依存境界・回帰を実行します。共通契約/時計/保存/描画管理を変更した場合は両モードを検査します。30分の試験や全ブラウザ全条件は正式候補でまとめて行い、毎回の文章変更に重い検査を課しません。正式候補で必要な試験を省く理由にはしません。

最終修正が入ったら候補SHAを更新し、影響範囲の試験を再実行します。影響を限定できなければ正式試験を再実行します。実機・公開確認が未了なら100点を付けず、その項目をBLOCKEDまたはNOT_RUNとして残します。
