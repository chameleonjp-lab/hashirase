# 05 Workへの依頼文・進捗管理

## 1. 計画を読む範囲

最初にREADME、01のユーザー要件、02の対象領域、03の指定作業、04の関連する検査を読みます。毎回全リポジトリを漫然と読み直すのではなく、対象ファイルと直接の依存先を確認します。ただし、参照範囲を狭めるために必要な仕様や失敗ログを省略してはいけません。

既存のAGENTS.md等がある場合は最新mainで読んで従います。計画の対象SHAから更新されていたら差分を先に確認します。計画に載っていない実装が追加されていた場合は、削除せず統合方法を記録します。

## 2. 1作業を依頼する共通プロンプト

```text
対象: chameleonjp-lab/hashirase
基準計画: docs/plans/hashirase-100/
今回の作業: Txx（この1作業だけ）

1. 最新main、PR #2のマージ、今回の作業の依存先完了をGitHubで確認する。
2. README、01の確定要件、02の対象契約、03のTxx、04の対応検査を読む。
3. 対象ファイルと直接の依存先を調査し、共有ファイルの担当競合を確認する。
4. 専用ブランチで、先に期待条件を検査するテストを書く。
5. 意図した失敗を確認し、指定範囲を実装する。ダミー実装・テスト削除・根拠のない条件緩和は禁止。
6. 対象テスト、既存検査、影響する回帰試験を実行する。正式ログと画像を保存し、画像は実見する。
7. tracker.jsonと証拠索引を更新する。今回実施していない実機項目はNOT_RUNのままにする。
8. GitHubへDraft PRを作成し、Actionsで失敗した場合は原因を調べ、解消して再検査する。
9. 最後にPR URL、head SHA、対象作業、合格/未実施、残る阻害要因を報告する。

mainの直接変更、勝手なマージ、課金設定変更、別作業への無断拡大はしない。
停止や時間切れの際は、保存先と再開箇所を具体的に残す。未提出のPRを提出済みと報告しない。
```

## 3. 最初の機能実装依頼

```text
chameleonjp-lab/hashirase の docs/plans/hashirase-100/ に従い、T01だけを実施してください。
PR #2がマージ済みか確認し、最新mainと計画の差分を記録してください。
既存の構文検査だけでなく、試験場→都市→リセットの実行検査を追加してください。
特にACTIVE_RENDER_RADIUS_SQの参照範囲、起動例外なのに成功表示する処理、車両部品の初期位置保存を先に再現してください。
起動を通す最小修正は、整理変更と別コミットで行ってください。
T02以降のモード分割やUI刷新は、この依頼には混ぜないでください。
証拠と未検証事項を保存し、Draft PRを提出してGitHubの検査結果まで確認してください。
```

## 4. 並行依頼に追加する指定

T02の契約が承認された後のT03/T04/T06、T07完成後のT08/T10/T12が基本の並行枠です。共有ファイルの変更は1担当に集約し、統合担当が順番に取り込みます。T05のホームをT06担当が同時に書き換えることは禁止し、T06は単体の入力/設定UIとfixtureを先に完成させます。

並行担当の依頼には「担当作業ID」「変更してよいフォルダ」「変更禁止の共有ファイル」「使用する契約版」「統合先」を付けます。分けすぎて停止が増える場合は並行数を減らし、1作業ずつ終えます。

## 5. 状態の意味

| 状態 | 意味 |
|---|---|
| NOT_STARTED | 未着手。計画に書いてあるだけでは実装済みではない |
| IN_PROGRESS | 専用ブランチで作業中。保存された差分と次の作業が分かる |
| IN_REVIEW | PR提出済み。検査・レビュー・マージの状況を記録する |
| DONE | 作業の完了条件が全て満たされ、ユーザーのマージが確認できた |
| BLOCKED | 具体的な前提が満たせない。理由・確認した事実・解消条件を書く |

検査の状態はNOT_RUN/PASS/FAIL/BLOCKEDです。コードのマージと実機検査の完了は別々に記録します。DONEの作業があっても、その評価軸の受入検査が未実施なら100点にはなりません。

tracker.jsonは最初は全作業NOT_STARTED・全検査NOT_RUNです。これは機能未実装の正しい初期状態であり、不合格結果を隠すための空欄ではありません。

## 6. 各PRの本文

```text
目的と対象作業: Txx
前提: 依存作業ID、参照したmain SHA、契約版
変更: 対象ファイル、ユーザー要件との対応、意図した挙動差
検査: コマンド、成功/失敗、対象SHA、Axxの状態、ログと画像
未検証: 実機、性能、外部環境を明記
残課題: 不具合ID、影響、今回範囲に含めない理由
戻し方: 戻すコミットまたは前の成果物、保存形式の互換性
マージ: ユーザー本人が実施
```

## 7. 停止時の引継ぎ

引継ぎには、最後に保存できたコミット、作業ブランチ、PRの有無、既に実行した検査、失敗したコマンドと省略前ログ、次に修正する関数、実機確認の有無を残します。

「残りは後で自動実行する」「確認待ちだが作業中」とは書きません。実際に保存されていない変更を復元可能と扱いません。新しいWorkでは最新GitHub状態を読み、重複PRを作らず既存PRがあれば続けます。

## 8. 計画を変更する場合

ユーザー要件の変更、テストで判明した矛盾、性能実測による方式変更は、変更理由を先に記録し、02・03・04・tracker.jsonを同じPRで更新します。要求の削除で採点を上げる、実測前に達成を宣言する、未確認の値を実車仕様へ格上げする変更は禁止します。
